# 食刻桌面卡片重设计方案

日期：2026-10-03。用户已确认执行 A 版 2×2 与带封面的 2×4。当前阶段：代码已实施，静态审查完成，等待用户编译及真机验证；详见 `IMPLEMENTATION.md`。

## 设计稿

- `direction-a.png` / `direction-a.svg`：A，食物优先，推荐实施。
- `direction-b.png` / `direction-b.svg`：B，口味记录，以评分为视觉中心。
- `direction-a-cover.png` / `direction-a-cover.svg`：按用户后续要求补充的 A 版 2×4 封面方案，左文右图；最新推荐组合为 A 版 2×2 与此带图 2×4。
- 每版包含 2×2、2×4 的浅色和深色示意。
- 示意画布以 160×160、340×160 逻辑尺寸表达比例，并非所有设备的固定卡片尺寸；落地时依宿主实际空间适配。
- 标题、分类、地点和 4/10 评分沿用用户截图。¥18.00 为排版示例，不代表该推荐的实际价格。
- 带图方案使用项目现有面包分类插画表达图片区域，黄油可颂、8/10 和 ¥12.00 均为示例；实际卡片展示该推荐的真实主图与数据。

## 修改前的问题与依据

`entry/src/main/ets/servicecard/pages/ServiceCard.ets` 在一个纵向容器内叠放 32vp 图标标题、最多两行的产品名称、评分价格和固定 48vp 的双按钮；外部还有 16vp 内边距和 10vp 行间距。这个结构难以容纳在小尺寸卡片中，符合截图中的底部裁切现象。

评分文案 `4/10 好味评分` 没有可收缩的宽度约束，而价格使用剩余宽度，容易被挤成 `¥…`。修改前 `form_config.json` 只声明 `2*2`。

参考华为官方[鸿蒙卡片设计指南](https://developer.huawei.com/consumer/cn/doc/design-guides/harmonyos-widget2-0000002731312633)，采用核心信息优先、克制配色、清晰主体和少量交互。参考官方[时钟卡片示例](https://developer.huawei.com/consumer/cn/codelab/Clock-Card/)中为 2×2、2×4 分别组织信息的做法；该示例是旧 Java 卡片，仅借鉴构图思路，当前项目继续采用 ArkTS / Form Kit。

本机 SDK `@ohos.app.form.formInfo.d.ts` 定义 `Dimension_2_2 = 2`、`Dimension_2_4 = 3`。不依赖网上非官方示例对这些数值或自动注入字段的假设。

## 最小实施方案：必做项

| 项目 | 执行内容 | 预期结果 |
| --- | --- | --- |
| 两种尺寸 | 保留原 `ServiceCard` 的名称与 2×2 默认规格；在同一卡片下新增 2×4 规格，按持久化尺寸分别渲染布局 | 兼容远端固定 formName，卡片选择器提供两种规格，旧实例保留原标识 |
| 信息层级 | A 版以产品名称为核心；小卡用短评分 `4/10`；大卡左侧展示名称、评分、价格，右侧预览封面 | 避免长标签占满宽度，名称和价格更易扫读 |
| 操作 | 内容区域打开详情；顶部独立刷新控件，视觉图标与触摸区域分别设置；两者使用互不覆盖的点击区域 | 去除双按钮占用的整行空间，刷新不误触跳转 |
| 刷新语义 | 保留现有本地缓存摘要刷新，不把按钮改成“换一家”；保留已有数据代理同步 | UI 文案与实际行为一致 |
| 文本适配 | 按实际可用宽高设置行数、字体范围和间距；名称最多两行，地点单行；价格与短评分分别约束；不足时先压缩留白、再精简辅助信息 | 小卡、长标题及放大字体时优先保住名称、价格和操作，避免底部越界 |
| 数据兜底 | 兼容现有远端 `scoreText` 和本地缓存；有效评分才显示数值，异常或缺失时显示“未评分”；缺失价格显示“价格待补充” | 不制造分数，不把默认引导文案当作价格 |
| 2×4 封面 | 读取该推荐的主图，复用公开已审核媒体下载缓存，并补充 Form Kit 图片绑定；封面等比裁剪于右侧，点击与正文进入同一条详情 | 桌面直接预览推荐照片 |
| 图片一致性 | 图片缓存同时记录所属 `cardId` 和图片身份；切换摘要时仅允许匹配的新图，否则立即使用缺图占位 | 避免新标题配旧照片 |
| 图片失败兜底 | 无图、下载失败、缓存被清理时，显示中性占位并保持名称、评分、价格可读；远端文字更新时不能继续显示上一条推荐图片 | 离线及异常情况下仍可使用 |
| 空状态 | 无 `cardId` 时显示“附近值得一试”和“打开食刻，发现好味道”，不展示伪造评分价格；点击进入现有附近入口 | 首次添加卡片时有明确、真实的引导 |
| 主题与无障碍 | 沿用已有 surface / ink / muted / accent / accent_soft 色彩资源；独立检查深色文字对比度；刷新提供无障碍名称，装饰图标不重复播报 | 两种主题一致，读屏可理解各操作 |
| 静态审查 | 修改后逐项核对 ArkTS 严格模式、对象字面量类型、Object 边界、资源名称、组件参数、卡片配置与路由 | 先完成代码静态审查，再交付用户编译验证 |

实际改动：`servicecard/pages/ServiceCard.ets`、新增 `ServiceCardPresentation.ets`、`ServiceCardCoverCache.ets`，修改 `ServiceCardStore.ets`、`ServiceCardFormAbility.ets`、`ServiceCardInteraction.ets` 及卡片尺寸/文字/主题资源，新增深浅色图标。在 `NearbyPage.ets` 增加下载期间推荐切换后的远端推送前检查；保留该文件已有改动。

2×4 沿用同一个 FormExtensionAbility 和 ServiceCardStore。客户端与云端按 `formId` 管理同步，两个尺寸接收同一份公开摘要。`shike-service/runtime.js` 在六个文字字段之外新增 `photoPath`、`photoBucket` 图片身份字段，从 CardMedia 读取主图元数据。图片字节仍由应用前台通过现有公开媒体接口缓存，再通过 Form Kit 传递。应用关闭时收到未缓存的新推荐先显示占位，下次前台发布该推荐时补齐图片；本轮不实现后台下载新封面。

## 可选项与未来扩展

| 级别 | 内容 | 预期结果 |
| --- | --- | --- |
| 可选 | 2×4 添加现有分类插画，明确为分类装饰，且在小尺寸隐藏 | 增加美食氛围；需要重新平衡信息空间 |
| 未来 | 多图预览与封面选择 | 在单张真实封面落地后扩展，需要补充多图数据与交互 |
| 未来 | 真正的“换一家” | 需有可轮换候选摘要和明确切换逻辑，不能仅更改当前刷新按钮文案 |

建议本轮实施必做项，采用 A 版 2×2 与带封面预览的 2×4。

## 实施后由用户执行的验证顺序

本轮未执行构建、运行测试、设备或浏览器测试。以下步骤在代码落地、静态审查完成后使用。

1. 在 DevEco 编译应用。预期无 ArkTS / 资源 / Form Kit 配置错误。若失败，反馈首条完整错误、文件行号与上下约 20 行日志。
2. 更新安装后查看原有 2×2，并在卡片选择器添加 2×2 和 2×4。预期两规格可选，原实例仍可显示，两种尺寸有不同布局。反馈选择器截图及两规格桌面截图。
3. 分别切换浅色、深色，以及默认和最大系统字体。预期无内容越界、评分价格互挤、底部操作裁切；名称和价格可读。反馈每个异常场景的截图。
4. 用已有可用推荐查看长名称、长地点、10/10、缺失价格，以及初次无摘要的情况。预期长文有合理省略，完整内容可在详情查看；无评分或价格时显示对应占位。若现有数据不足，先反馈缺少哪个场景，再安排数据准备，不直接改生产数据。
5. 点刷新，然后点内容区域。预期刷新保持桌面并重绘本地缓存，内容区域打开对应详情；无推荐时打开附近入口。刷新没有改变推荐时可以是正常现象，因为该操作不请求新推荐。
6. 在应用内产生现有推荐更新，同时观察两个尺寸。若已启用远端同步，再沿现有同步流程检查。预期两个尺寸都更新，布局保持各自规格；反馈异常前后截图及脱敏日志。
7. 检查带图推荐、无图推荐、断网或图片缓存失效，再切换另一条推荐。预期有图时展示对应真实封面，失败时显示占位；新推荐不可沿用上一条照片。反馈切换前后及失败状态截图，注明应用是否在前台。

反馈附设备型号、HarmonyOS 版本、桌面网格设置、字体设置及问题对应步骤。运行结果未返回前，不宣称已通过真机适配。
